# 函数思维脚手架 · 优化建议（面向「以后还会大量加题」）

- 日期：2026-11-14
- 前提：试卷题库已拆成 `题库/packs/*.js` 分片，主包从 1.92 MB 降到 309 KB（见
  `docs/plans/函数思维脚手架-题库分片-2026-11-14.md`）
- 这份文件只讲**接下来该改什么、为什么、改哪几行**；不重复「怎么加一道题」（那是
  `数学/题库工具/README.md` 的事）

## 0. 先看一个数：现在一套卷的 85% 是图

| 分片 | 总大小 | 内联图 | 占比 | 图张数 |
|---|---:|---:|---:|---:|
| `pk-fanbi-2708.js` | 217 KB | 183 KB | 84% | 12 |
| `pk-hanshu-1014.js` | 462 KB | 430 KB | 93% | 24 |
| `pk-qimo-mn-1028.js` | 237 KB | 183 KB | 77% | 14 |
| `pk-qimo-1105.js` | 175 KB | 110 KB | 63% | 11 |
| `pk-week11-1111.js` | 482 KB | 428 KB | 89% | 17 |
| **合计** | **1.54 MB** | **1.30 MB** | **85%** | 78 |

文字题（题干/解析/公式/选项）五套加起来只有 **约 240 KB**。

**结论：以后加题，体积几乎全部来自图，不是来自文字。** 所以「怎么加题不把仓库撑爆」，
90% 的答案在图片上；文字部分按现在的密度，加 10 套卷也才多 500 KB。

## P0 · 继续加题之前先做（3 条，收益最大）

### 1. 把内联图改成外部图片引用（省 85% 体积）

**现状**：`fig` / `hand` 字段里是 `data:image/webp;base64,…`，base64 比原图**再胖 33%**，
而且每次 build 都会把同一张图重新写进分片，git 里每改一次就多存一份完整图片。

**改法**：`题库/` 下已经有现成的图（`<卷名>- 答卷附图/q<题号>.webp`、
`2026-2027学年度第一学期期中- 附图/*.png`）。把字段改成路径：

```json
"hand": { "w": 900, "h": 209, "src": "题库/第11周周练- 答卷附图/q1.webp" }
```

页面里 `<image href="题库/…webp">`，`file://` 下能直接显示（`<img>`/SVG `href` 不受 CORS 限制）。

- 收益：5 个分片 **1.54 MB → 约 240 KB**；图片由浏览器缓存，翻来覆去看不重复下载；
  git 里图片只存一份，改文字解析时不再连带重存几十张图。
- 代价：`qb.py bundle`（发手机的单文件版）要**在打包时把图片读回来内联**——多 20 行代码，
  正好 `bundle` 已经是「把外部的东西塞回一个文件」的角色。
- 落点：`qb.py` 的 `chunk_text()` 旁边加一个 `externalize_figs(pack)`；
  `bundle` 里反向 `inline_figs()`；`check-pack.mjs` 的 `fig`/`hand` 检查同时接受 `src` 和 `svg`。
- 先做一张图验证：改 `pk-week11-1111` 的第 1 题，跑 build + 打开页面确认图还在，再批量。

> 如果不想动 schema，退一步：`hand.py` / `figs.py` 生成时用 **WebP 质量 55 + 宽度 ≤ 720**
> 再嵌。现在这些图是按手机看手写定的尺寸，很多可以直接砍一半。这也能省 40% 左右，
> 但只是把问题推迟。

### 2. 让 `pack-全部.json` 退出入库

**现状**：`题库/pack-全部.json` 1.55 MB 被 git 跟踪，内容 = 5 个分片的合并，**和分片完全重复**。
它只在 `qb.py build`（合并）和 `verify`（比对）里用，页面运行时不读。

按仓库自己的判据「页面或构建运行时读它吗」——它是构建中间产物，应该本机留档：

```gitignore
数学/题库/pack-全部.json
```

- 收益：每次 build 少一个 1.55 MB 的 blob；仓库不再随加题线性膨胀。
- 代价：新机器 clone 后第一次 `verify` 会报「pack-全部.json 不存在」——把 `verify` 里那段
  改成「不存在就跳过并提示先 build」即可（现在是在 `try` 里报 ✗）。
- 注意：`build` 的排序依赖它（`order = [...read_json(ALL_JSON)['packs']]`），
  所以删掉后**卷顺序会变成文件名字典序**。如果在意顺序，把顺序写进一个小的
  `题库/packs.order.json`（几行，入库）。

### 3. 把 `score` 从「建议」升级成「硬性」

**现状**：`pk-fanbi-2708` 23 题**一个分值都没有**，后果是这套卷：
- 「录得分」页直接是空的（`函数思维脚手架.html:5792` `if(!scored)`）；
- 得分档案里没有它的板块得分率；
- 首页任务卡的「得分」口径少一套卷。

`qb.py verify` 对 `score` 只是**打印提示**（`qb.py` 的 `score 必须是正数` 分支），缺了不报错。
以后加卷越多，漏填分值的卷越多，得分档案就越没用。

**改法**：`verify` 里加「每套卷 ≥ 80% 的题有 score，否则报错」；顺手给 `pk-fanbi-2708` 补分值
（老师版答案卷上就有）。**这条不做，加再多卷也换不来一句「这次比上次多拿了几分」。**

## P1 · 加到 15 套以上会开始疼（3 条）

### 4. 分片按需加载（懒加载）

**现状**：页面加载时 5 个分片**全部同步执行**，加 10 套卷就是首屏解析 3～4 MB JS。
本地 `file://` 大概几十毫秒，还能忍；但手机上是真会卡。

**改法**：主包里只放一个清单（id / 卷名 / 题数 / 满分 / 每题 id，约 10 KB），
点开某套卷时再插 `<script src>`：

```js
function loadPack(id, cb){ /* 已加载直接 cb；否则建 <script>，onload 后 cb */ }
```

- 挡路的不是加载器，是 **`render()` 的同步假设**：`viewPack` / `viewPaperQ` /
  `viewScoreEntry` / `scoreReportHTML` 都假定 `findPack()` 立刻有 `questions`。
- 最小切法：只让「题目列表」以后的屏走异步，`viewPaper` 列表页和首页统计只用清单。
  加载中显示一行「正在载入…」，加载完再 `render()`。
- 收益：首屏从 1.5 MB 降到 ~15 KB；加 30 套卷首屏不变。
- 建议**先做第 1 条（图外置）再做这条**——图外置后首屏只有 240 KB，懒加载的紧迫性会下降很多。

### 5. 题目 id 规范 + 加题查重

**现状**：题 id 是 `b1`、`w11q5`、`m21` 这类手写短名，跨卷唯一全靠人记。
`check-pack.mjs` 只查**卷内**重复（`:89` `ids.has(q.id)`）。

- 加题多了以后，同一道题从不同卷录两遍几乎一定会发生。
- **建议**：新卷统一 `q.id = <卷短名>-<题号>`（如 `w12-05`）；`check-pack.mjs` 加一条
  「全库题干前 30 字 + 选项集合」相似度查重，命中就打印「疑似重复：w11 第 5 题 / w12 第 9 题」。
  30 行代码，能在加题阶段就拦住。

### 6. build 前预检 + 生成题库索引

**现状**：`qb.py build` 先写盘再让你 `verify`；结构错了要回滚 `.bak`。
另外「一共有哪些卷、每套多少题多少分、覆盖哪些知识点」只能翻 `使用说明.md` 或打开页面。

- **预检**：`build` 开头先跑一遍 `verify` 的结构检查（不写盘），不合格直接退出。
- **索引**：`build` 顺手生成 `题库/索引.md`（卷名 / 题数 / 满分 / kp 分布 / 最近改动时间），
  一眼能看出「二次函数还缺题」「这套卷没分值」。这是纯生成物，10 行代码。

## P2 · 诊断能力（2026-11-12 审计就指出来了，仍然没修）

这三条不影响「加题」，但决定「加了题能不能看出效果」。

| # | 问题 | 证据 | 改动量 |
|---|---|---|---|
| 7 | **算不出「分在哪一步」**：分步判分的 `detail` 只在内存里算出来显示，落库时被丢掉 | `函数思维脚手架.html:5568` 算出 `detail`；`:6632` 写库时只留 `score/got/sec/err` | 写库时加 `detail:g.detail`，报告页读它 —— 约 6 行 |
| 8 | **录得分路径没有错因**：`saveScores` 恒写 `err:null` | `:5846` | 录得分行内加三选一（`err`）—— 约 8 行 |
| 9 | **板块口径是 `kp[0]`**：一题挂多个知识点时，得分全算给第一个 | `:5507` `kpOf` | 按 kp 全量分摊，或在报告里注明「按主知识点归类」—— 约 10 行 |

第 7 条价值最高：现在能回答「哪块分少」，回答不了「这一步为什么断」，
而后者才是这个工具存在的理由。

## P3 · 工程卫生（2 条，做起来快）

### 10. 把这次用的浏览器探针固化成脚本

这次验证用的是 `chrome-headless-shell --dump-dom` + 一段注入的探针脚本（见任务卡第五节的实测结果），
是临时手搓的。`工具/qa/` 里已经有 `mk-t-math.mjs` 这类「生成探针 HTML」的脚本，但没有
「跑起来 + 断言 + 退出码」的一层。

**建议**：加 `工具/qa/run-probe.mjs <html> <期望标题>`，用 chromium headless 跑一遍、
抓 `<title>`、`ALL_PASS` 就退出 0。这样「改完引擎跑一次」是一条命令，而不是开浏览器手点。

### 11. 单卷超 700 KB 的拆卷约定

`build` 现在会在分片 > 700 KB 时提示，但没有说怎么办。约定写死：

- 一套卷拆成 `pack-<卷>-上.json` / `pack-<卷>-下.json`，`id` 用 `pk-xxx-a` / `pk-xxx-b`，
  `name` 里标明「（上）/（下）」。页面按卷显示，拆开后就是两张卡片。
- 别按知识点拆——现在的组织单位是「卷」，按知识点拆会让「整卷重做」这个主用法失效。
