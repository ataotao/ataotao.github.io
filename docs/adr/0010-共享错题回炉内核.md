# ADR-0010：错题回炉规则抽成共享内核，四科产物内联同一份

- 状态：已采纳（2026-11-19）
- 相关：`docs/规范/错题回炉统一规范.md`（**后续所有项目必须遵守的生效规范**）、`docs/plans/错题回炉规则统一-2026-11-19.md`、`工具/trainer/review.js`、`GLOSSARY.md`
- 取代：四科原先各自实现的错题回炉逻辑

## 背景

四科闪练卡的错题回炉规则长期各自演化，到 2026-11-19 已明显分叉：

- 解除判据：数学"任何模式答对即删"、物理"回炉答对才删"、化学"回炉答对/手动删"、英语"到期后连对 2 次"。三科存在"蒙对一次即解除"的漏洞。
- 间隔算法：四科都写死 1/3/7/14 天阶梯，且都是在答错时用 `now + gap*DAY` 重排——虽然已是绝对时间戳（不依赖日历天数），但间隔本身不是由用户历史作答时间动态推断的。
- 代码归属：数学/物理/英语是 scaffold 三源（各自 `源/train.ui.js`），化学在 `工具/trainer/kernel.js` 的 UI 模板里。同样的规则写了四遍，改一处必漏三处。

用户要求：统一规则、真正掌握才算通过（不能蒙对）、间隔基于历史练习时间戳动态计算、便于维护。经 grill 确认五条决策（连对 2 次 + 行为约束、阶梯 + 实际时间戳重算、共享模块、分科用时阈值、手动掌握改跳过）。

## 决定

1. **新增共享内核 `工具/trainer/review.js`**：纯函数式，不碰 DOM、不碰 localStorage、不认识任何科目；只处理错题条目的调度字段（`ts/due/n/lvl/okStreak/lastOkAt/lastAt`）与状态转移。各科传入题目快照与行为信号（是否到期、用时、是否看提示、是否订正），内核返回动作（入库/保留/移出）。
2. **分科差异留在配置里**：用时阈值、错题键生成、题目标识字段由各科提供；内核不含任何科目名或阈值常量。这样"统一规则"与"科目个性"边界清楚。
3. **构建时内联同一份源码**：`build.mjs` 增 `<script id="review">` 段，四科产物都内联 `review.js` 的逐字节相同内容。产物仍是单文件、`file://` 可双击；改规则只改一处再重建四科（遵守 ADR-0003）。
4. **规则细节**（见任务卡）：连对 2 次移出；无效答对（未到期/秒答/看提示/订正）连对清零并重排 `due`；答错回退一档；`due = now + gap(lvl)*DAY` 永远基于当前真实时间戳；手动"已掌握"改为"跳过本次"（只推 `due`，不删除）。
5. **旧数据平滑迁移**：缺 `lvl` 按 `n` 推导，缺 `okStreak` 补 0，`due` 不动——不重置用户已有计划。

## 后果

- **收益**：规则只有一处真相源，四科一致；蒙对一次不再能解除错题；间隔由真实作答时间驱动，跳过几天不累计欠账也不误判。
- **代价**：改规则要重建四科产物并跑四套自检；产物体积各增约 2–3 KB（共享内核内联）。
- **兼容**：记录键、错题键、深链契约、开始页统计口径都不变；云同步合并对新增字段走通用互补，`n` 仍取 max。
- **为什么不用"四科各放一份相同实现"**：那个方案改动面小，但靠人肉同步四处，正是这次分叉的成因，等于把 bug 复发机制保留下来。
- **为什么不"完全按历史间隔推断、去掉 1/3/7/14 阶梯"**：用户练习不规律（可能隔几天才练），纯历史间隔在冷启动和长间隔后无稳定基准；阶梯提供下限骨架，`now + gap*DAY` 提供动态性，兼顾两者。

## 追加决定（2026-11-19）：历史错题留档供期末复盘

用户追问"错题删除后是否还留历史，期末要统计曾经错过的题复盘"。确认现状：连对达标时删的只是 `DB.wrong` 那一条待复习条目，**`DB.recs` 每笔作答（含每次 `ok:false`）永久留档**，导出 JSON 与云同步都会带走——历史本来就没丢，缺的是查看入口。经 grill 定：复用 `recs` 流水（不新增归档存储）、报告页加「曾经错题」清单、去掉化学 `recs` 截断。

6. **`everWrong(recs, wrongMap)` 从作答流水聚合历史**：按 `qid` 归并，输出题目标题、累计错/对次数、首错/末错时间戳、是否仍在错题本；错次降序。错题库条目在答错入库时补写同源 `qid`（旧条目在再次答错时补），用于对账"现在还在不在本"。新规则下移出错题本的唯一途径是连对 2 次有效答对（"跳过本次"不删），所以"不在本 = 已掌握"成立。
7. **状态语义**：`recs` 是长久事实层，`DB.wrong` 是当前待办层，两层独立。掌握后清单里那一行不消失，只把状态从「在错题本」翻成「已掌握」——这正是期末复盘要的"曾经错过、现已掌握"轨迹。
8. **去掉 recs 的 2000→1500 截断（两处）**：`kernel.js` 提交段与共享 `merge.mjs` 云同步合并段都曾砍掉最老的 500 条——只改一处会被另一处抵消。整学期作答是复盘原始依据，两处都去掉；单条约 200 B，几千条在 localStorage 5 MB 配额内。`merge.test.mjs` 补 2200 条不截断断言。
9. **边界**：「在错题本」判断依赖错题条目有 `qid`；升级前就已存在、此后再没答错过的旧条目没有 `qid`，会被判成"已掌握"——一次性数据瑕疵，不影响历史流水本身。清了浏览器存储则两层皆空，需靠导出的 JSON 长期保存（与 ADR-0001/0007 的快照哲学一致）。

**为什么不新增 `wrongHistory` 归档区**：答错事件已经在 `recs` 里全量留档，再加一份完整题目快照会双份存储、还要写迁移，收益只是"重做时能直接拿到原题面"——而期末复盘的第一需求是"统计哪些题曾经错过"，`recs` 已满足；题面可按 `qid` 回题库取。若将来要做"一键生成历史错题重做卷"，再单独评估。
